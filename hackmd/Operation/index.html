    持續整合工具會定義了整合的觸發時機。例如當某一個分支有合併發生、或是新增了一個新的發佈標籤時，持續整合工具就會從版本管理系統取得相關的程式碼進行下一個動作

    相關的程式碼會進行一些基本的測試。例如檢查發的程式是否合乎相關開發語言的標準(Coding Standard)，又或者是程式中是否有漏洞(Vulnerabilities)。如果檢查時發現程式未能合符發佈的要求時，整合工具可以中止相關的發佈動作

    成功通過了自動化的測試後，相關的程式會被打包成為可以被引用的套件，或者是可運行的Docker Image等，並上載到儲存倉庫中，以便日後利用

    版本管理工具例如GitLab等，亦是市面上比較多人使用的整合工具之一。它的好處是把整合工具跟版本管理放到同一套工具中，在管理上會更加方便。而缺點亦因為整合了版本管理系統的關係，如果有需要使用多套版本管理系統時，可能在整合上會增加了操作及整合上的繁複性

    Think of your .gitlab-ci.yml file as the blueprint. Runners are the machines that carry out the work.

    When the pipeline runs it's the GitLab Runners that pick up these jobs and execute them according to the pipeline configuration.

    GitLab’s runner system includes: - GitLab Runner – the actual software installed on a machine - runners – the agents that execute pipeline jobs

    Each runner runs inside an environment defined by an executor like Docker or Shell.

    The DevOps Swag Store uses three different runners: - A Docker-based runner for test and build jobs - A shell runner on a secure server for deployments - A macOS runner for mobile app testing (in beta)

    In GitLab, there are two main types of runners - GitLab-hosted Runners: Hosted by GitLab - SaaS runners are enabled by default on GitLab.com projects. When a pipeline runs, GitLab spins up a fresh virtual machine (VM) just for that job. The VM is deleted after the job completes. - Self-Managed Runners: Hosted by you - If you use a self-managed GitLab instance, you must register your own runners.

    Runner Types Different runner scopes—Instance, Group, and Project—determine where jobs can run and how broadly runners are shared. - Instance runners are shared across every project in a GitLab instance. - Group runners are available to every project within a specific group. - Project runners are dedicated to specific projects and must be explicitly enabled in the project’s settings.

    Runner-Executor Relationship While a runner picks up CI/CD jobs from GitLab, the executor determines how and where those jobs are run. - Runner: Connects to GitLab, polls for jobs, manages overall execution. - Executor: The method the runner uses to run the job’s commands. - Shell executor runs commands directly on the host machine - This executor type is ideal for scenarios where simplicity and direct interaction with the host system are priorities. - Docker executor creates a new container for each job, ensuring that tasks run in isolated environments. - This approach is particularly useful for running frontend build and test jobs, as it minimizes interference between processes. - Kubernetes executor runs each job in a pod - an excellent choice for cloud-based scaling. It is frequently used for mobile build jobs that require high levels of concurrency and resource management. - SSH executor connects to a remote machine via SSH to execute commands - This executor type is ideal for maintaining compatibility with older infrastructure while transitioning to modern solutions.

  - trigger-services
  - global-deploy

# 觸發服務 A 的流水線（獨立執行，互不干涉）
trigger-service-a:
  stage: trigger-services
  trigger:
    project: microservices-group/service-a
    branch: main
    strategy: depend # 核心關鍵：確保服務 A 完全成功後，此工作才算 Success

# 觸發服務 B 的流水線（與服務 A 平行觸發）

    Pipeline 執行控制（Execution Control）與條件分支

    Use rules with an regex if-statement 

    stages:
  - deploy

deploy-to-production:
  stage: deploy
  image: alpine:3.20
  rules:
    # 關鍵：只有當提交事件為 Tag，且格式符合 vX.Y.Z 時才執行
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
      when: on_success
    # 其他情況一律不加入 pipeline (預設為 when: never)
  script:
    - echo "Deploying release version $CI_COMMIT_TAG to production cluster..."
    - ./scripts/deploy.sh

    關鍵字 tags 的雙重含義（認證必考）： - $CI_COMMIT_TAG：內建環境變數，代表當前觸發的 Git Tag 名稱。 - job 中的 tags: 屬性：用來指定執行該工作所需的 Runner 標籤。 - Job 頂層的 tags 是用來選擇指定的 GitLab Runner（如 tags: [k8s-runner]），與 Git Tag 毫無關係。

    GitLab CI/CD Secret Variables

    延伸考 Masked 與 Protected 變數的行為差異 - Masked Variables（遮罩變數）： - 核心功能：防止變數值不小心被 echo 印出時暴露在 GitLab pipeline log 中。GitLab 會自動將日誌中的該字串替換為 [masked]。 - Protected Variables（保護變數）： - 核心功能：只有在「被保護的分支（Protected Branches，如 main）」或「被保護的 Git Tag」上執行的 pipeline 才能讀取到該變數

    GitLab CI/CD 容器化服務整合（Services in GitLab CI/CD）

    當你使用 Docker Executor 時，services 允許你指定多個 Docker 映像檔。GitLab Runner 會在主 job 容器啟動的同時，在同一個網路（Network）中額外啟動這些附屬容器。主容器可以透過主機名（例如 mysql）直接連線到該服務，非常適合資料庫或快取服務的配置。 - services 關鍵字必須在 Docker 或 Kubernetes Executor 之下才能正常運作。如果你的 Runner 是傳統的 Shell Executor，宣告 services 將完全沒有任何效果

    GitLab CI/CD 合規性與安全治理（Compliance & Governance）

    在現代軟體開發中，一個專案往往引入數百個開源第三方套件。然而，並非所有開源授權（Licenses）都能在企業內自由使用，例如某些具備強傳染性的開源授權（如 GPL 系列），若不小心誤用在商業專案中，可能會面臨極大的法律訴訟與合規風險（Compliance Risks）。License Scanning 解決的就是「如何由系統自動審查程式碼中所有第三方套件的授權清單，防止不合規的授權隨程式碼進入生產環境」的法務痛點。

    License Scanning 的底層運作原理： ~~- 考試常考概念：「License Scanning 如何得知第三方套件的授權？」 它是透過分析專案中的 套件管理宣告檔案（例如：package.json、pom.xml、go.mod、requirements.txt），並將抓到的套件名稱與官方授權資料庫進行比對。如果專案內根本沒有這些檔案（或沒有跑套件安裝預檢），授權掃描將無法有效工作。~~

    新考題問法：現代 GitLab 核心如何執行 License Scanning？ 答案：解析由相依性掃描生成的 CycloneDX SBOM 檔案（Parsing CycloneDX SBOM files）。

    與 Dependency Scanning 的區隔（極高頻考點）： - 題目出現 known vulnerabilities（已知漏洞）、CVE、security fixes $\rightarrow$ 請選 Dependency Scanning。 - 題目出現 legal team（法務團隊）、compliance（合規）、policies、open-source libraries codes $\rightarrow$ 請選 License Scanning。

    CI/CD 自動化與災難恢復（Disaster Recovery & Automation）

    最標準的配置方式是將 environment 與 action 進行聯動 

    stages:
  - deploy

deploy_to_production:
  stage: deploy
  script:
    - echo "Deploying version $CI_COMMIT_SHA to production..."
    - ./scripts/ansible-deploy.sh --version $CI_COMMIT_SHA
  environment:
    name: production
    url: https://my-app.com
    on_stop: rollback_production # 宣告與回滾任務的聯動

rollback_production:
  stage: deploy
  script:
    - echo "Critical failure detected! Rolling back to previous stable version..."
    # 實戰中通常是重新指派或啟動上一次成功的 Docker Tag 或 K8s 部署清單
    - ./scripts/ansible-deploy.sh --rollback-to-last-stable
  environment:
    name: production
    action: stop # 宣告此動作為停止/回滾目前部署
  when: manual # 關鍵：平常不自動執行，只在出事時由運維人員一鍵 Play 啟動
