    Question 3

    • Gateway API | Kubernetes
      • How to set gatteway api with HTTPS tls cert - General Discussions - Discuss Kubernetes

    在 Ingress 時代，一個 YAML 檔案通常要包含 IP 綁定、證書、路由規則，這導致維護上的混亂。Gateway API 將其拆解，讓對的人做對的事 這是 Gateway 最核心的貢獻。它將網路配置劃分為三個獨立的控制點：

    • 基礎設施層 (GatewayClass)：解決「誰來提供負載平衡器」的問題。
      • 以前：管理員必須全局設定 Ingress Controller。
      • 現在：可以同時存在多個 GatewayClass（例如：一個對外的 AWS ALB，一個對內的 Cilium L7），互不干擾。
    • 網路進入層 (Gateway)：解決「流量在哪個連接埠、用哪個證書進入」的問題。 這由 叢集管理員 掌控。他們定義 VIP、TLS 憑證和安全策略，而不需要關心後端路由。
    • 應用路由層 (HTTPRoute)：解決「特定路徑要導向哪個 Service」的問題。
      • 這由 應用開發者 掌控。他們只需定義自己的路由邏輯，無法動到 Gateway 的安全設定（如證書或埠號）。

    GatewayClass的概念類似StorageClass，負責定義實際上處理底層的Controller(Provisioner)是哪一個

    需要先理解原本kind: Ingress的意思，spec.tls會出現在Gateway，spec.rules會出現在HTTPRoute

    用"gateway api"搜尋，進入Gateway API | Kubernetes後，在該頁面找"TLS"，會找到TLS Configuration | Gateway API

    ，~~官網沒有找到HTTPS的範例，要注意一下。用"gateway api with HTTPS"搜尋，會看到這篇How to set gatteway api with HTTPS tls cert - General Discussions - Discuss Kubernetes，裡面有HTTPS的範例 注意複製貼上的時候有特殊字元會讓kubectl apply失敗 "error converting YAML to JSON: yaml: line 8: found character that cannot start any token"~~

    Question 9

    NetworkPolicy

    要讓 Network Policy 生效，需要在 cluster 中安裝支援 Network Policy 的 CNI - 支援 Network Policy 的CNI: Calico、Cilium、Weave Net - 不支援的 CNI: Flannel

    規則適用的「方向」: ingress/egress ingress: 控制外部對 Pod 的網路流量 (誰可以連進來?) egress: 控制 Pod 對外的網路流量 (可以出去連到誰？)

    規則適用的「對象」: pod/namespace/ipBlock pod: 使用 podSelector 指定 namespace: 使用 namespaceSelector 指定 ipBlock: 使用 ipBlock 指定，意指「對特定的 IP 範圍(CIDR)生效」，通常會設定為 cluster 外部的 IP

    Network Policy 並不會彼此衝突，而是會將所有的「白名單」相加形成「白名單聯集」

    Question 12

    PersistentVolume, PVC and deployment

    • persistentVolumeReclaimPolicy: Retain
      • STATUS 為 Released，代表原本的 PVC 已被刪除，但 PV 尚未被回收，所以無法再被其他 PVC 綁定使用
      • 將 claimRef 設為 null 就可以手動回收 PV，讓它的 STATUS 變回 Available

    用"change pv"搜尋，可以找到類似的範例，小改一下

    kubectl patch pv <pv name> -p '{"spec":{"claimRef": null}}'

    Question 13

    cri-dockerd

    在 Kubernetes 1.24 版本之後，官方移除了內建的 dockershim。如果你想繼續使用 Docker 作為容器引擎，就必須安裝 cri-dockerd 作為中介層（Adapter），讓 Kubernetes 的 kubelet 能夠透過標準的 CRI 介面與 Docker 通訊。

    dpkg -i
systemctl start

    設定系統內核參數（Network Bridging） 

    sudo sysctl -w net.bridge.bridge-nf-call-iptables=1
sudo sysctl -w net.ipv6.conf.all.forwarding=1
sudo sysctl -w net.ipv4.ip_forward=1
sudo sysctl -w net.netfilter.nf_conntrack_max=131072

    make it persistent 

    vi /etc/sysctl.d/kube.conf
# add the config
net.bridge.bridge-nf-call-iptables=1
net.ipv6.conf.all.forwarding=1
net.ipv4.ip_forward=1
net.netfilter.nf_conntrack_max=131072


    sudo sysctl --system

    Question 14

    Troublshooting for kube-apiserver and etcd, Debug Master Node

    有某種方式可以不需要 kube-apiserver 的指示，讓 kubelet 自己建立新的 Pod，亦即static pod 是 kubelet 管理的 Static pod: /etc/kubernetes/manifests/

    檢查kube-apiserver的狀態 

    sudo crictl ps -a | grep kube-apiserver

    若CRI為containerd，在/var/log/pods查一下pod log ex. /var/log/pods/kube-system_kube-apiserver-cplane-01_c81cd1ede43a8da7cfb3b21e6bf0c218/kube-apiserver/xxx.log

    有些 cluster 中的 kube-apiserver 不是用 static pod 跑的，而是用 systemd 服務跑，用journalctl查一下log 

    journalctl -u kube-apiserver.service

    Cluster 的重要元件都會有固定的 port： - kube-apiserver：6443 - etcd：2379-2380 - etcd 的 2379 是 client port，2380 是 peer port (多台 etcd server 之間通訊的 port) - kube-scheduler：10259 - kube-controller-manager：10257 - kubelet：10250

    常見變化類型: IP錯誤或憑證/金鑰位置錯誤

    • /etc/kubernetes/pki
    • /var/lib/kubelet/pki

    其他debug方式 

    journalctl -u kubelet -f

    Question 15

    Taints & Tolerances - https://ithelp.ithome.com.tw/articles/10347661

    • 想像 Kubernetes 叢集是一個社區：
      • Node 是一間公寓。
      • Taint 是公寓門口的告示牌，寫著「內有大型犬」。
      • Pod 是想要入住的租客。
      • Toleration 是租客的一項特質，比如「我不怕狗」。 如果不怕狗的租客（Toleration）來到這間公寓，他就能住進去；但一般的租客看到告示牌就會被嚇跑，去尋找其他沒有標籤的公寓。
    kubectl taint --help

    k get node
k describe node node-1 | grep -i 'taint'
k taint -h

    搜尋"Taints"可以找到建立pod的範例 

    k get pod -o wide
